# README·데이터 대조와 담당자 확인

SETUP에서 첫 질문을 만들 때 읽고, DISCOVER나 BUILD에서 새 정보 공백이 드러나면 해당 부분을 다시 적용한다. 목적은 프로젝트의 요구사항과 산출물을 구현하는 데 필요한 정보를 확보하는 것이다. 요구사항과 업무 규칙을 추측으로 확정하지 않는다.

## 1. 산출물에서 입력까지 역으로 대조

README의 REQ·필수 산출물별로 다음을 `docs/INTERVIEW.md`의 데이터 대조표에 적는다.

- 무엇을 계산·판정·표시·저장해야 하는가: 출력 필드, 단위·집계 기준, 결과 형식.
- 어떤 입력과 규칙이 있어야 하는가: 파일·컬럼·식별자·참조 테이블·기간·업무 정책.
- 제공 데이터가 어디까지 뒷받침하는가: 실제 경로·컬럼·관계·대표 행과 확인한 집계. 표본 분석이면 범위와 한계를 표시한다.
- 무엇이 아직 없는가: 파일 자체 부재 / 컬럼·참조 관계 부재 / 값 누락 / 의미·규칙 미정 / 표본에 없는 경계 사례. 연결할 GAP ID를 적는다.

파일 목록·안내된 경로·제공 데이터 사전을 먼저 확인한다. 파일이 없다는 것과 파일을 아직 못 찾았다는 것을 구분한다. CSV 등 구조화 데이터의 정확한 행 수는 형식에 맞는 파서로 확인하며, 단순 줄 수나 일부 표본을 전체 레코드 수로 단정하지 않는다. 원본 데이터는 수정하지 않는다.

## 2. 결과가 달라지는 지점만 우선 조사

REQ와 관련된 다음 관점을 선택해 점검한다. 전체 체크리스트를 기계적으로 질문하거나 범위 밖 기능을 요구하지 않는다.

| 관점 | 데이터로 볼 것 | 담당자에게 확인할 것 |
|---|---|---|
| 자료·참조 정보 | 필요한 파일·컬럼, 코드표·기준값·매핑 부재 | 추가 자료 위치·제공 가능 여부, 없을 때의 업무 처리 |
| 식별자·관계 | 키 중복, 조인 불일치, 예상과 다른 1:N·N:M | 중복이 오류인지 이력인지, 매칭 기준·대표 행 선택 규칙 |
| 값의 의미 | NULL·빈 문자열·0·음수·단위·상태 코드 | 미측정과 실제 0의 구분, 유효 범위, 알 수 없는 값의 처리 |
| 시간·집계 | 시간대, 기간 경계, 지연 도착·수정 이력 | 포함/제외 경계, 기준 시각, 최신값·최종 상태·취소 반영 기준 |
| 판정·예외 | 임계값 근처, 동률, 누락된 그룹, 분모 0 | 우선순위·동률 규칙, 제외·보류·오류 중 기대 동작 |
| 처리·산출물 | 재입력·중복 처리, 부분 실패, 출력 순서·반올림 | 재처리 의미, 허용되는 부분 결과, 필수 출력의 표현·정밀도 |

**데이터에서 보이지 않았다고 발생하지 않는다고 가정하지 않는다.** 실제 규칙을 바꿀 수 있는 '경계 바로 아래·같음·바로 위', '일치·불일치·다중 일치' 등의 최소 반례를 고른다. 가상 사례는 질문·테스트용임을 표시하고 관측 사례처럼 말하지 않는다.

## 3. GAP 우선순위와 질문

- **P0:** 필수 산출물에 필요한 자료·규칙이 없어 구현 또는 결과의 정확성 판정이 막힘.
- **P1:** 구현은 가능하지만 예외 처리에 따라 결과·데이터 무결성이 달라짐.
- **P2:** 선택적 품질 개선이나 부가 맥락. 시간 부족 시 뒤로 미룬다.

각 GAP은 관찰 근거, 연결 REQ, 질문, 답에 따라 바뀔 구현을 가진다. 한 번에 1~2개를 제안하며 담당자가 쓸 수 있는 업무 언어로 묻는다. 선택지를 제시해도 '다른 기준이 있는지' 열어 두고 원하는 답으로 유도하지 않는다.

예시 — 실제 프로젝트에 해당할 때만 구체적 이름·수치로 바꾼다:

- **누락 자료:** 'README의 지점별 매출 산출에는 지점 매핑이 필요한데, 제공 주문 파일에는 고객 ID만 있고 안내 경로에서도 매핑을 찾지 못했습니다. 별도 파일이나 연결 기준이 있나요? 매핑할 수 없는 주문은 현업에서 어떻게 처리하나요?'
- **관찰된 이상:** '같은 ID에 상태가 다른 행이 있습니다. 수정 이력인지 서로 다른 건인지, 어떤 값으로 구분해야 하나요?' 답을 받으면 최신 시각이 같은 가상 사례로 대표 행 규칙을 추가 확인한다.
- **표본에 없는 예외:** '임계값과 정확히 같은 값은 표본에 없고 README에는 “초과”와 “이상”이 명시되지 않았습니다. 같은 값일 때 기대 판정은 무엇인가요?' 경계 아래·같음·위의 기대 결과를 되읽는다.

예상한 선택지만 확인하고 끝내지 않는다. 중요한 처리 흐름 하나를 설명한 뒤 '이 흐름에서 제공 표본에는 없지만 현업에서 수동으로 예외 처리하는 최근 사례는 무엇이며, 그때 어떤 결과가 맞았나요?'처럼 구체적인 업무 상황을 짚어 아직 발견하지 못한 예외도 끌어낸다. 새로운 정보는 관련 REQ와 영향을 대조해 GAP으로 추가한다.

## 4. 답을 해결로 바꾸는 조건

1. 담당자 답의 핵심 문구·시각·조건을 보존한다. 조건을 생략한 요약이나 Codex의 해석을 담당자 발언으로 적지 않는다.
2. 추가 자료를 받거나 위치를 안내받으면 프로젝트에서 접근 가능한 경로에서 실제 파일·스키마·필요 값·관계를 확인한다. '파일이 있다'는 답만으로 확보 완료가 아니다.
3. 업무 규칙은 구체적인 입력 → 기대 결과로 바꾸어 담당자에게 되읽는다. 답이 정상 사례만 설명하면 결과가 갈리는 반례 하나를 더 확인한다. 규칙이 테스트 가능한 수준으로 명확해졌는지 본다.
4. README·데이터·답변이 충돌하면 충돌 근거와 영향을 남기고 재질문한다. 담당자의 설명으로 필수 요구사항을 삭제하거나, 데이터의 다수 사례를 정답으로 삼지 않는다.
5. GAP 상태를 **미확인 / 질문 중 / 추가 자료 대기 / 충돌 / 확인 완료 / 미해결·가정 진행** 중 하나로 기록한다. 필요한 자료가 확인되고 규칙·기대 결과가 명확하며 충돌이 해소된 경우에만 확인 완료로 바꾼다. 가정 진행은 사용자 결정 ID와 남은 위험을 붙이고 확인 완료와 구별한다.

확인된 GAP의 원문·근거는 INTERVIEW에 유지한다. AGREEMENT는 관련 REQ·확정 규칙·미해결 영향을 연결하고, DECISIONS는 선택의 이유, VERIFICATION은 입력·기대 결과·실행 증거를 연결한다. 담당자 확인은 실행 검증의 대체물이 아니다. 자료를 못 받았으면 합성 테스트가 통과해도 실제 데이터에 대한 REQ 충족을 주장하지 않는다.
