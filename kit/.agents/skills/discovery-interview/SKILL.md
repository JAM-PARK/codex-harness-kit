# Discovery Interview

**권장 모델·effort:** 6.1 Sol / medium. 모순되는 증거 때문에 문제 정의를 다시 판단해야 할 때만 해당 분석을 high로 올린다. 실제 설정 확인은 `AGENTS.md`의 전환 규칙을 따른다.

## 역할 분담 (가장 중요)

- **현업 담당자 또는 담당자 역할의 에이전트와의 인터뷰는 사용자가 직접** 한다. 담당자가 없는 프로젝트는 사용자가 확인 주체가 된다. Codex는 담당자를 대신 연기하거나 답을 생성하지 않는다. 담당자와 나눈 대화가 문제 정의·업무 규칙의 근거 기록이 된다.
- 담당자는 요구사항을 한 번에 정리해 주지 못하는 경우가 많다. 목록을 달라고 하기보다 사다리를 따라 끌어낸다.
- 너는 질문을 제안하고, 사용자가 붙여 넣은 답을 기록·분석한다.
- 담당자의 답을 추측해서 채우지 않는다. 기록에는 사용자가 전달한 내용만 쓴다.
- 질문 목록을 한꺼번에 길게 주지 않는다. 사용자가 자연스럽게 물을 수 있게 한 번에 1~2개만 제안한다.

## SETUP — 데이터 사전 점검 (첫 질문은 5분 안에)

1. `references/data-gaps.md`를 읽고 적용한다. `assets/INTERVIEW.md`를 바탕으로 `docs/INTERVIEW.md`를 만든다. 이미 있으면 기록을 보존해 이어 쓴다.
2. README의 필수조건·산출물마다 필요한 입력·업무 규칙·기대 결과와 실제 데이터 근거를 대조한다. 파일 목록·스키마·대표 행과 요구사항 관련 집계를 보고, 분석 범위가 전체인지 표본인지 적는다. 모든 데이터를 샅샅이 분석하느라 질문을 늦추지 않는다.
3. 파일·컬럼·참조 데이터 부재, 값 누락, 의미·판정 규칙 미정, 데이터에 나타나지 않은 엣지 케이스를 GAP ID로 구분한다. 먼저 작업 공간과 안내 문서에서 확인 가능한 것은 확인하고, 제공 정보로 알 수 없는 것만 담당자 질문으로 만든다.
4. 구현을 막거나 필수 산출물의 결과를 바꾸는 GAP부터 첫 질문 1~2개를 제안한다. **관찰 근거 → 모르는 점·구체적 사례 → 확인할 업무 처리·필요 자료 → 구현 영향**을 담는다. 정상 사례만으로 결론 내리지 않고 결과가 달라지는 반례를 고른다.

## DISCOVER — 답변으로 정보 공백 닫기

SETUP의 대조표와 GAP을 이어 쓴다. 담당자가 원하는 해결책은 '요청', 데이터에서 관찰한 것은 '사실', 확인 전 처리 규칙은 '가정'으로 나눈다. 답을 받으면 입력 사례와 기대 결과로 되읽고, 해당 파일·규칙·경계 사례를 다시 확인한다. 빠진 자료가 어디에 있는지, 제공 가능한지, 제공할 수 없을 때 업무상 어떤 처리가 맞는지까지 확인한다. 상세 질문 방식과 해결 판정은 `references/data-gaps.md`를 따른다.

## 질문 사다리

담당 업무 맥락을 짧게 확인한 뒤 아래 관점에서 빈칸을 찾는다. 모든 단계를 순서대로 소진하지 않는다. 구현을 막는 GAP이 있으면 자료·규칙 확인을 먼저 하고, 답변에 따라 관련 관점으로 돌아온다.

1. **맥락**: 담당 업무, 하루 흐름, 이 일이 얼마나 자주 생기나
2. **최근 사례**: 가장 최근에 이 문제 때문에 곤란했던 일을 언제·누가·무엇을·결과까지
3. **현재 우회 방법**: 지금은 어떻게 버티나, 어떤 도구(엑셀, 메신저, 기존 시스템)를 쓰나
4. **정량화**: 빈도·시간·비용·오류의 현재값, 그리고 그 숫자를 어떻게 아는지(측정 출처)
5. **관계자**: 누가 쓰고, 누가 결과를 보고, 누가 승인하나
6. **경계와 제약**: 데이터 접근, 보안·외부 반출, 사용 환경(PC·브라우저·설치 가능 여부), 바꿀 수 없는 것
7. **성공의 모습**: 이게 해결되면 내일 무엇이 달라지나
8. **되읽기**: 이해한 내용을 3줄로 요약해 맞는지 확인

## 규칙과 이유

- 문제를 충분히 듣기 전에는 해결책·자동화·AI 이야기를 꺼내지 않는다. 담당자가 처음 말한 해결책은 진짜 필요와 다를 때가 많다.
- "제가 할 일을 정리해 주세요", "요구사항 목록을 주세요" 같은 지름길 질문은 하지 않는다. 문제를 스스로 정의해야 진짜 필요를 놓치지 않는다.
- 숫자를 들으면 출처를 묻고 데이터와 대조한다. 담당자의 체감과 데이터가 다르면 그 차이가 좋은 질문거리다.
- 모르는 용어·약어는 바로 묻는다.
- 새 정보가 기존 가설을 뒤집으면 숨기지 말고 가설을 고친다. 바뀐 이유도 적는다.

## 답변이 쌓이면 (묶어서 분석)

사용자는 담당자의 답을 `docs/INTERVIEW.md`의 '대화 요점'에 붙여 넣는다. 일반 맥락 답변은 2~3개씩 묶어 분석하되, 구현을 막는 자료·규칙·충돌에 대한 답은 즉시 대조한다. 분석할 때:

1. 질문 원문·담당자 답의 핵심 문구·조건·출처·시각을 기록하고 GAP ID를 연결한다. 관찰 사실과 담당자 설명을 구분한다.
2. 답변을 데이터·README와 대조해 GAP 상태와 기대 결과를 갱신한다. 실제로 확보한 자료와 '있다고 안내받은 자료'를 구분한다. 모호한 답에는 정상·경계 사례를 붙여 후속 확인한다.
3. 확인된 규칙의 REQ·산출물·설계·테스트 영향을 적고, 남은 GAP 중 우선순위가 높은 질문 1~2개를 이유와 함께 제안한다.

## 종료 조건 (작업 시간의 15% 안에)

- 문제 진술 1문장: [누가] [어떤 상황에서] [무엇 때문에] [어떤 손실]을 겪는다
- 현재값이 있는 수치 1개 이상, 제약 2개 이상, 핵심 사용자 확인
- 모든 REQ·필수 산출물에 필요한 데이터·규칙의 확보 여부가 대조표에 있고, 중요한 GAP은 확인 완료 또는 미해결 이유·다음 조치가 명시되어 있다
- 확인된 주요 예외는 구체적 입력과 기대 결과로 남아 있으며, 해당 REQ·구현 작업·검증 사례에 넘길 수 있다

조건을 채우면 사용자에게 요약을 보여주고 design-agreement 스킬로 넘어가자고 제안한다. `docs/STATE.md`를 AGREE로 바꾸고 커밋한다 (`docs: 인터뷰 정리`).

시간이 다 됐으면 조사 범위를 좁히고 미해결 GAP·영향·다음 조치를 AGREE로 넘긴다. 핵심 자료 부재를 임의 값이나 가짜 데이터로 메우지 않는다. 가정으로 진행 가능한 부분은 사용자에게 선택지와 영향을 제시하고 결정받아 표시한다. 필수조건을 막는 GAP은 STATE의 '막힌 점'에도 남기고, 독립적으로 진행 가능한 작업부터 한다. BUILD에서 새 GAP을 발견해도 관련 질문만 다시 열고 인터뷰 전체를 반복하지 않는다.
