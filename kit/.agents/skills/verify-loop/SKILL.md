# Verify Loop

검증은 "됐다고 믿는 것"이 아니라 "됐다는 증거를 남기는 것"이다. 문서에 적은 주장과 실제 코드·커밋·실행 기록이 서로 이어져야 한다.

**권장 모델·effort:** 6.1 Sol / high로 상세 설계·구현·디버깅·검증 설계·독립 리뷰를 진행한다. 기존 검사의 실행·기록과 명세가 확정된 단순 반복 수정은 medium. 설계의 xhigh 전환은 `AGENTS.md`의 미해결 핵심 결정 기준을 따르며, 전체 BUILD나 리뷰의 기본값으로 쓰지 않는다.

## 작업 단위 루프 (매 작업마다)

1. **완료 조건 확인**: 공식 과제 문서와 `docs/AGREEMENT.md`에서 필수조건·작업의 완료 조건을 다시 읽는다. 합의에 빠진 공식 필수조건도 검증 대상이다.
2. **자동 검사**: 있는 것만 실행한다 (타입체크, 린트, 테스트, 빌드). 명령과 결과(통과·실패 수)를 `docs/VERIFICATION.md` 실행 기록에 적는다. 처음이면 `assets/VERIFICATION.md`를 복사해 만든다.
3. **실제 실행 확인**
   - 웹 화면: 서버를 `0.0.0.0`에 띄우고 포트·경로와 수동 확인 절차를 사용자에게 전달한다. **사용자가 플랫폼 Browser에서 직접** 데모 단계를 밟고 결과를 알려준다. 에이전트는 로컬 서비스에 대한 `curl`·CLI 테스트로 HTML·API 응답을 확인한다. Computer Use, 브라우저 자동 클릭·입력·화면 캡처 도구는 사용하지 않는다. 사용자 확인 전에는 UI 검증을 미실행으로 기록하고, 보고받은 결과와 직접 실행한 CLI 증거를 구분한다.
   - 데이터 처리: 작은 표본을 손으로, 또는 본 코드와 독립된 짧은 스크립트로 계산한 값과 비교하는 골든 테스트를 만든다.
4. **경계 사례**: 해당하는 것 중 최소 2개를 테스트한다 — 빈 값, 중복 행, 형식 불일치(대소문자·공백·구분자·날짜 형식), 시간대, 0으로 나누기, 큰 입력.
5. **추적표 갱신**: VERIFICATION.md의 'REQ / SC ↔ 구현 위치 ↔ 증거' 표를 갱신한다.
6. **범위 점검**: `git diff --stat`으로 합의 밖 변경이 없는지 본다. 있으면 되돌리거나 사용자 승인을 받는다.
7. **3줄 보고 후 커밋**: ① 무엇을 ② 왜 이 방식 ③ 어디서 깨질 수 있나.

## 기준 수치와 결과가 다를 때

기존 수작업 결과나 참고 수치와 내 결과가 다르면 **코드를 기준에 맞추지 않는다**. 차이를 분해한다: 어느 행, 어느 규칙(중복 처리, 제외 기준, 형식 정규화, 집계 방식)에서 갈리는가. 규칙별로 차이를 재현해 합계가 맞아떨어지는지 보인다. 설명이 끝나면 담당자에게 어느 규칙이 맞는지 묻는 질문을 만든다. 차이를 설명한 기록은 그 자체로 강한 검증 증거다.

## 제품 안에서 LLM을 쓸 때

- 응답은 JSON 스키마로 검증하고, 실패하면 1회 재시도한 뒤 안전한 대체 경로(규칙 기반 결과나 "검토 필요" 표시)로 간다.
- 판정·계산을 LLM에 맡기지 않는다. LLM이 만든 문장에는 '초안' 표시를 한다.
- 응시 환경에서 명시적으로 허용된 방식이 있는 경우에만 구현한다. 개인 API 키·별도 AI 연결을 요구하거나 과제 데이터를 외부 API·MCP·Plugin에 전송하지 않는다. 허용된 연동이 없으면 결정적 코드나 사용자 검토 경로로 범위를 정한다.

## 실패했을 때

같은 오류로 두 번 실패하면 멈춘다. 가설 2개와 각각의 확인 방법을 사용자에게 보고하고, 가장 작은 재현 사례로 확인한다. 원인과 조치는 `docs/DECISIONS.md`의 '오류·복구 기록'에 남긴다. 테스트가 틀렸다고 판단되면 고치기 전에 이유를 기록한다. AI가 틀린 지점을 잡았으면 같은 곳에 한 줄 남긴다: 무엇이 틀렸나 → 어떻게 잡았나 → 무엇을 바꿨나. 나중에 결과를 설명할 때 재료가 된다.

## 독립 리뷰 (E2E v0 직후, 기능 동결 직후)

작성 맥락에 물들지 않은 시선으로 본다. 제공된 Codex 안에서 6.1 Sol / high를 권장하며, 새 세션에서도 `/status`·`/model`로 실제 설정을 확인한다. 리뷰 모델·effort를 확인할 수 없으면 6.1 Sol / high를 확인한 일반 세션에 아래 리뷰 요청문을 준다. 모델·설정 제한을 우회하지 않는다.

- `/review`가 있으면 쓴다. 작업 단위마다 커밋했다면 '커밋되지 않은 변경'이 비어 있으니 비교 기준(기준 커밋이나 브랜치)을 지정한다.
- `/review`가 없거나 결과가 비면, 다른 터미널 탭에서 새 Codex 세션을 열고 `references/review-prompt.md`의 내용으로 요청한다.

결과는 심각도별로 VERIFICATION.md에 적고, **무엇을 고칠지는 사용자가 정한다**. 모든 지적을 고치려 하지 말고 공식 필수조건·SC에 미치는 영향이 큰 것부터 처리한다. 고치지 않기로 한 것은 이유와 함께 '알려진 한계'에 남기며, 필수조건 미충족을 합의만으로 통과 처리하지 않는다.
