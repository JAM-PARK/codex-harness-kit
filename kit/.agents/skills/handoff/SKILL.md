# Handoff

인수인계 문서는 두 가지 일을 한다. 새 세션이 맥락을 잃지 않고 이어가게 하고, 사용자와 다음 담당자가 설계·구현·운영 방법을 이해하도록 돕는다.

**권장 모델·effort:** 6.1 Sol만 사용한다. 세션 교대·인수인계 문서 정리·마무리 확인은 medium, 코드 이해와 심화 self-quiz·모범답안·피드백은 high. 다음 세션에는 `AGENTS.md`의 해당 작업 권장값을 전달한다.

이해 점검은 코드 리뷰·온보딩·인수인계에 활용한다. 구현이나 요구사항이 바뀌면 관련 문답도 갱신한다.

## 모드 A — 세션 교대

언제: AGREE 완료 직후, E2E v0 완료 직후, 기능 동결 직후, 또는 대화가 길어져 응답 품질이 떨어질 때.

긴 대화를 계속 압축하며 버티는 것보다 정해진 시점에 끊고 문서로 넘기는 편이 정확하고 비용도 적다.

1. `assets/HANDOFF.md`를 바탕으로 `docs/HANDOFF.md`를 갱신한다. 다른 문서에 이미 있는 내용은 반복하지 말고 경로만 적는다.
2. '다음 세션 첫 지시문'을 3줄 이내로 쓴다.
3. `docs/STATE.md`를 갱신하고 커밋한다 (`docs: handoff — <단계>`).
4. 사용자에게 Codex의 새 세션(`/new`, 없으면 Codex 재시작)을 열고 `/status`·`/model`로 6.1 Sol과 다음 작업의 권장 effort를 확인한 뒤 이렇게 시작하라고 안내한다: "AGENTS.md와 docs/HANDOFF.md를 읽고 '다음 세션 첫 지시문'부터 이어가." 도구 업데이트나 관리 설정 변경은 하지 않는다.

## 모드 B — 마감 (작업 시간의 마지막 15%, 85% 시점부터)

1. 구현과 리뷰 반영을 멈춘다. 남은 작업은 '다음 단계 제안'으로 옮긴다.
2. `docs/HANDOFF.md`를 최종본으로 완성한다. 독자는 담당자 팀에서 이 도구를 이어받을 엔지니어다. 실행 방법은 복사해서 바로 돌릴 수 있게 쓴다.
3. **인수인계 연습**: `references/self-quiz.md`를 읽고 설계·의사결정·데이터베이스 중심의 심화 질문을 최대 6개 만든다. 기본으로 모든 문항에 모범답안·코드 근거·꼬리질문과 답안 요점을 붙여 `docs/SELF_QUIZ.md`에 저장하고 HANDOFF에서 연결한다. 사용자 답변을 기다리지 않고 문답 자료를 먼저 완성한다. 남은 시간이 부족하면 문항 수를 줄이되 각 문항의 모범답안은 생략하지 않는다. 사용자가 원하면 한 문제씩 풀고 피드백받는 연습을 진행한다.
   - 최소 한 문항은 README·데이터의 정보 공백을 담당자 Q&A로 확인하고 결정·구현·검증에 반영한 과정을 다룬다. 문항 수를 줄여도 이 관점은 유지하며, 담당자 답이 없으면 실제 미확인·가정과 그 영향을 설명한다.
   - 최적화·ML이 있으면 관련이 낮은 일반 문항을 교체해 라이브러리/확장/직접 구현의 선택 근거와 알고리즘 검증·평가 한계를 다룬다. 총 6개 이내에서 각 문항에 모범답안·실험 근거·꼬리질문 답을 포함한다.
4. 프로젝트 요구사항 문서가 정한 필수 파일명·경로·내용과 모든 REQ / SC의 검증 결과를 확인한다. 실행 방법은 지정된 위치(없으면 `docs/HANDOFF.md`)에 쓴다. 합의된 변경이 있다면 관련 문서도 일치시키고 변경 이력을 남긴다.
5. 작업 변경을 커밋하고 `git status`로 남은 변경을 확인한다. 사용자가 진행 중인 변경은 보존하고 별도로 보고한다.
6. 종료 10분 전부터 아래 마무리 확인을 진행하고 완료한 것·미완료한 것·다음 작업을 보고한다. 로컬 커밋과 원격 반영·배포는 별개로 확인한다.

## 마무리 확인

1. 필요한 파일·경로·내용과 저장 상태를 확인한다.
2. 실행·테스트 방법을 따라 결과를 확인하고, 미실행 검사와 알려진 한계를 기록한다.
3. 인수인계 문서에 다음 작업·의존 정보·남은 결정을 정리한다.
4. 원격 반영·공유·배포가 요청 범위에 있다면 프로젝트 절차에 따라 수행하고 결과를 확인한다. 포함되지 않으면 필요한 후속 작업으로 남긴다.
5. 사용자에게 산출물 위치·검증 결과·남은 위험·다음 시작점을 안내한다.
