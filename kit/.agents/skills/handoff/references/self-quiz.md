# 심화 이해 점검 — 질문과 모범답안

코드 리뷰·온보딩·인수인계에서 결과물의 설계와 구현을 이해하기 위한 문답이다. 남은 작업 시간에서 문서 정리와 전달 시간을 먼저 확보하고, 시간이 부족하면 문항 수를 줄인다.

6.1 Sol / high를 권장한다. 사용자의 결과물에 대한 **질문과 모범답안을 항상 한 세트로** 최대 6개 만든다. 실제 코드·스키마·쿼리·커밋·결정·검증 기록을 근거로 작성한다. 단순한 기능 소개나 용어 정의 대신, 설계 선택의 이유와 그 선택이 보장하는 것·깨지는 조건을 설명하게 한다.

## 근거 수집과 깊이

- 프로젝트 README와 `docs/INTERVIEW.md`의 데이터 대조표·GAP·담당자 Q&A, `docs/AGREEMENT.md`·`docs/DECISIONS.md`·`docs/VERIFICATION.md`와 핵심 구현을 읽는다. 요구사항 → 부족 정보 → 담당자 확인 → 결정 → 구현 → 검증의 연결과 입력 → 출력의 실제 경로를 따라 질문 소재를 고른다.
- 각 문항은 실제 파일·함수·테이블·쿼리·결정 ID를 짚고, **왜 이 선택인가 → 어떤 반례에서 깨지는가 → 어떻게 확인·개선할 것인가**까지 묻는다. 조건을 바꾼 구체적인 꼬리질문 1개와 답안 요점도 붙인다.
- 현재 구현의 사실, 기록에 없는 의도의 추론, 미구현 개선안을 구분한다. 의사결정 기록이 없으면 이유를 지어내지 말고 '기록 없음; 코드로부터 추론'이라고 표시한다. 테스트하지 않은 보장·성능 수치·장애 복구를 검증된 것처럼 쓰지 않는다.
- DB가 없어도 데이터 관점 문항은 유지한다. CSV·JSON·메모리 등 실제 저장 방식의 식별자·중복·관계·재시작 시 보존·동시 쓰기 한계를 묻고, DB로 옮길 조건과 필요한 제약을 **가정한 개선안**으로 설명한다. 없는 테이블·인덱스·트랜잭션을 만들어 답하지 않는다.

## 질문 유형 (6문항 기준)

아래는 선택할 관점이다. 항목의 모든 기술을 한 문항에 몰아넣지 말고 결과물에 중요한 쟁점에 집중한다. **최소 한 문항은 데이터 분석과 담당자 Q&A로 부족한 정보를 도출·확인한 과정**을 다룬다(2번에 통합해 총 6개 이내 유지). 시간이 짧으면 1~3을 우선하고, 더 부족하면 문항을 합치거나 줄이되 설계·의사결정·데이터 관점과 이 확인 과정, 모범답안을 남긴다.

1. **설계와 책임 경계**: 실제 요청이나 데이터 한 건이 모듈·계층을 통과하는 경로와 각 책임을 설명하게 한다. 로직을 현재 위치에 둔 이유, 다른 계층으로 옮겼을 때 결합도·테스트·실패 전파가 어떻게 달라지는지 묻는다.
2. **정보 도출과 의사결정**: 실제 GAP 하나를 고른다. 어떤 REQ·산출물 때문에 정보가 필요했고 제공 데이터만으로 왜 판단할 수 없었는지, 어떤 관찰·반례로 질문했으며 담당자 답으로 무엇을 새로 알았는지 묻는다. 그 답이 데이터 모델·처리 규칙·대안 선택·테스트를 어떻게 바꿨는지, 확인하지 않았다면 어떤 오류가 생겼을지 설명하게 한다. 선택의 손익과 결정을 뒤집을 조건도 짚는다. 답이 없는 GAP은 미해결 이유·사용자 가정·영향을 다루고 확인한 것처럼 꾸미지 않는다.
3. **데이터 모델과 무결성**: 엔터티·관계·카디널리티, 기본키·업무 식별자, 중복·NULL·삭제 정책 중 중요한 부분을 고른다. 앱 검증과 DB 제약이 각각 어디까지 보장하는지, 정규화 또는 중복 저장의 손익과 갱신 이상을 실제 입력 예로 설명하게 한다.
4. **트랜잭션·동시성·실패 복구**: 실제 쓰기 경로에서 두 요청의 실행이 겹치거나 중간에 실패하는 순서를 제시한다. 어떤 상태가 남는지, 원자성의 경계, 재시도 시 중복·멱등성, unique 제약·잠금·격리 수준 중 관련된 수단이 있는지와 없는 경우의 위험을 묻는다. 읽기 전용이면 원본 갱신 중 조회의 일관성·재실행 재현성 문제로 바꾼다.
5. **쿼리와 성능**: 실제 필터·조인·집계·정렬 또는 파일 순회 한 곳을 고른다. 데이터가 10배가 될 때 병목 가설과 근거를 묻고, 인덱스의 컬럼 순서·쓰기 비용, N+1·페이지네이션·메모리 사용 중 관련된 대안 하나를 비교한다. 실행 계획이나 측정이 없으면 가설이라고 밝히고 검증 방법을 답하게 한다.
6. **전제 오류와 검증의 한계**: 실제로 없는 보장이나 잘못된 결정 이유를 전제로 묻는다. 예: 앱에서만 중복을 검사하는데 'DB가 중복을 완전히 막으니 동시 요청도 안전한 이유는?' 전제를 먼저 교정하고, 현재 테스트가 놓치는 반례·영향 범위·추가할 검증을 설명하게 한다.

## 정보 도출 문항의 필수 근거

모범답안에 **README의 REQ·산출물 → 데이터 관찰과 한계 → GAP 질문·담당자 답 → 결정·구현 위치 → 경계 사례의 기대 결과·실행 증거**를 연결한다. 데이터로 확인한 사실, 담당자에게 확인한 규칙, 사용자 가정, 미검증 부분을 구별한다. 자료를 추가로 받았다면 실제 확보·대조 결과도 설명한다.

꼬리질문은 '담당자 답이 없었다면 어떻게 처리할 것인가', '답과 데이터가 충돌한다면 무엇을 확인할 것인가', '표본에 없는 같은 경계 사례가 들어오면 어떤 결과가 나오는가' 중 해당하는 하나와 답안 요점을 쓴다. 질문만 잘했는지가 아니라 그 답을 구현·검증에 반영했는지를 점검한다.

Q&A 기록이 없으면 확인 과정을 만들어내지 않는다. 실제 README·데이터의 미확인 지점을 소재로 '무엇을 질문해야 했고 현재 어떤 가정에 의존하는가'를 묻고, 모범답안에도 담당자 미확인이라고 쓴다. GAP이 없다고 기록되어 있다면 그 판단의 근거·조사 범위·남은 한계를 점검한다.

## 문항별 출력 형식

### 최적화·머신러닝이 있는 프로젝트

총 6문항 안에서 일반 DB·트랜잭션 문항 등 관련이 낮은 문항을 교체해 아래 두 관점을 포함한다. 문항을 줄일 때는 합쳐도 되지만 담당자 Q&A로 정보를 도출한 관점과 함께 유지한다. 알고리즘이 없는 프로젝트에는 추가하지 않는다. 필요하면 `.agents/skills/design-agreement/references/algorithm-selection.md`의 평가 기준을 읽는다.

1. **라이브러리와 맞춤 설계의 선택:** 어떤 REQ 때문에 라이브러리 활용·확장·직접 구현 중 이 방식을 택했는가? 라이브러리에 맡긴 부분과 직접 설계한 목적함수·제약·특징·전처리·후처리는 어디인가? 버린 대안과 비교한 실제 근거, 요구사항이나 규모가 바뀌면 선택을 바꿀 조건은? 모범답안은 결정 ID·버전·지원 범위·실험 기록을 인용하고 '유명해서', '맞춤이라 더 좋아서'로 끝내지 않는다. 비교 실행이 없으면 설계 근거와 미검증 성능 가설을 구분한다.
2. **정확성·평가·실패 한계:** 최적화라면 실행 가능 해와 최적해를 어떻게 구분하며, 시간 제한·제약 충돌·반올림 시 무엇을 보장하는가? ML이라면 이 CSV의 시간·그룹 구조에서 왜 이 분할·지표를 택했고, 전처리 누수를 어떻게 막았으며, 단순 기준 모델보다 낫다는 근거와 일반화 한계는 무엇인가? 결합 방식이면 예측 오차가 후속 결정과 필수 제약에 미치는 영향도 묻는다.

두 관점 모두 질문·완결된 모범답안·코드/실험 근거·꼬리질문과 답안 요점을 제공한다. 꼬리질문은 '라이브러리가 이 제약을 지원하지 않으면?', 'solver가 시간 초과했지만 해를 반환하면?', '같은 고객이 학습·검증 양쪽에 있으면?', '라벨이 늦게 들어오면?'처럼 실제 위험에 맞춰 고른다. 실행하지 않은 비교 결과·최적성 증명·성능 향상을 만들어내지 않는다.

### 공통 형식

`docs/SELF_QUIZ.md` 상단에 작성 시각과 '구현 이해·인수인계용'을 적고, 각 문항을 다음 구조로 작성한다. 질문만 만들거나 키워드 목록을 모범답안으로 대신하지 않는다.

- **질문**: 실제 구현에 대한 심화 질문.
- **모범답안**: 아래 ①~⑤를 담은 5~8문장 안팎의 완결된 답안. 사용자가 자기 말로 설명할 수 있도록 쓰되 구현의 약점도 솔직하게 밝힌다.
- **근거**: 실제 파일·함수·테이블·쿼리 위치, REQ·GAP·결정 ID, 담당자 답변 위치·조건, 관련 테스트·실행 기록. 코드로 확인한 사실과 미검증 가설을 표시한다.
- **꼬리질문 + 답안 요점**: 입력·동시 요청·규모·요구사항을 바꾸었을 때의 판단과 이유를 1~3문장으로 적는다.

## 모범답안과 사용자 답변의 틀

① **결론**: 한 문장. 전제가 틀렸으면 "질문은 ~라고 했지만 실제로는 ~"로 시작
② **위치**: 어느 파일 · 함수 · 결정인지 구체적으로 짚는다
③ **근거**: 버린 대안, 담당자 확인, 테스트 결과, 숫자
④ **파급**: 왜 문제가 되는지, 영향이 어디까지 가는지
⑤ **다음 조치**: 무엇을 검증하거나 고칠지

## 기본 진행 — 문답 자료를 먼저 완성

- 질문·모범답안·근거·꼬리질문과 답안 요점을 모두 작성하고 `docs/SELF_QUIZ.md`에 저장한 뒤 사용자에게 경로와 우선 볼 문항을 안내한다. HANDOFF에도 링크를 남긴다. 답안 제공을 사용자 응답이나 별도 요청 뒤로 미루지 않는다.
- 마무리 시간을 먼저 확보한다. 문항 수·분량을 줄여도 남겨 둔 문항의 모범답안은 유지하고, 연습 때문에 작업 마무리를 늦추지 않는다. 이미 마무리 시점이면 산출물·후속 작업을 우선 정리하고 대화형 연습은 시작하지 않는다.
- 모범답안은 현재 결과물의 이해를 돕는 자료다. 답안에 쓴 개선안을 구현하려고 WRAP에서 코드를 바꾸지 않는다.

## 선택 진행 — 사용자가 직접 풀기를 원할 때

- 기본 문답 자료는 그대로 제공하고, 채팅에서는 한 번에 한 문제씩 낸다. 사용자는 답안 부분을 보지 않고 남은 시간에 맞춰 AI 없이 직접 답한다. 별도 요청이 없다면 이 방식으로 답변을 기다리지 않는다.
- 답을 받은 뒤 코드와 대조해 ①~⑤ 각각 충분 / 부족을 짧게 피드백한다. 전제 오류 문항은 바로잡았는지부터 본다.
- 사용자가 설명하지 못한 부분은 해당 코드를 함께 읽고 핵심을 3줄로 정리해 준다.
