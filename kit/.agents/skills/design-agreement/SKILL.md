# Design Agreement

구현보다 합의가 먼저다. 무엇을 만들지 않을지까지 정해 두어야 에이전트가 범위를 넓히지 않고, 나중에 검증할 기준도 생긴다.

## 1. 합의문 작성 (약 10분)

`assets/AGREEMENT.md`를 `docs/AGREEMENT.md`로 복사하고 `docs/INTERVIEW.md`를 근거로 채운다.

- 성공 기준(SC)은 최대 3개다. 각 SC에 지표·현재값·목표값·측정 방법을 쓴다. 측정할 수 없으면 SC가 아니다.
- '만들지 않을 것'을 최소 2개 쓴다. 담당자가 처음에 요청했지만 진짜 문제와 거리가 먼 해결책은 여기서 정리한다.
- 인터뷰에 근거가 없는 내용은 [가정]으로 표시한다.

## 2. 담당자 확인

사용자가 담당자에게 보낼 확인 메시지를 5줄 이내로 만든다. 보낼 때는 사용자가 자기 말로 다듬는다.

> 제가 이해한 문제는 ~입니다. 성공은 ~로 판단하려고 합니다. 이번에는 ~까지 만들고 ~는 제외합니다. [가정]으로 둔 ~도 맞는지 궁금합니다. 틀리거나 빠진 게 있을까요?

담당자가 고친 내용은 AGREEMENT에 반영하고 '변경 이력'에 남긴다. 확정되면 `AGENTS.md`의 '합의된 성공 기준'에 SC를 옮겨 적는다.

## 3. 최소 설계

- **구조**: 구성요소 3~5개와 데이터 흐름을 한 문단이나 간단한 다이어그램으로 쓴다.
- **핵심 결정 1~3개**: 선택지 2개와 트레이드오프를 사용자에게 보여주고 고르게 한다. 결과는 `assets/DECISIONS.md` 형식으로 `docs/DECISIONS.md`에 남긴다.
- **기술 선택**: 환경에 이미 있는 것을 우선한다 (`node -v`, `python3 --version`, 설치된 패키지). 설치·빌드 문제로 시간을 잃는 것이 가장 비싸다.
- **데모 시나리오**: 담당자가 3분 안에 가치를 확인하는 흐름을 3~5단계로 쓴다. 이것이 E2E v0의 목표다. 가능하면 제공 데이터 속 실제 사례(예: 담당자가 말한 최근 사고)를 재현하는 흐름으로 만든다.

## 4. 작업 분해

5~8개 작업으로 나눠 AGREEMENT의 작업 표에 적는다. 각 작업에는 다음을 쓴다.

- 연결된 SC
- 사용자가 결정할 것 / 에이전트가 구현할 것
- 완료 조건: 어떤 명령이나 화면으로 확인하는가
- 첫 작업은 데모 시나리오를 끝까지 관통하는 가장 얇은 버전(walking skeleton)이다. 화면이 투박해도 데이터가 입력부터 출력까지 흐르게 만든다.

## 과설계 점검 (설계 확정 전)

아래 중 하나라도 "예"면 줄인다.

- SC와 연결되지 않는 구성요소가 있는가
- 읽기 전용이거나 사용자가 적은데 동시성 제어, 권한 체계, 캐시 계층을 넣으려 하는가
- 담당자가 요청하지 않은 설정 화면, 관리자 기능, 범용 프레임워크가 있는가
- 결정적 규칙으로 충분한 판단을 LLM에 맡기려 하는가
- 제약(보안·외부 반출·설치 불가 등)을 어기는 구성이 있는가

## 종료

AGREEMENT 확정, DECISIONS 기록, 작업 표 완성 → `docs/STATE.md`를 BUILD로 바꾸고 커밋한다 (`docs: 합의문과 작업 계획 [SC-1..n]`). 이 시점에 handoff 스킬의 세션 교대 모드를 한 번 쓰는 것을 권한다.
