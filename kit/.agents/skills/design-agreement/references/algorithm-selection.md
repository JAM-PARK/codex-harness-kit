# CSV 기반 최적화·머신러닝 설계와 구현 방식 선택

CSV를 입력으로 최적화·머신러닝을 설계하거나 기존 라이브러리와 직접 구현을 비교할 때 적용한다. 단순 CSV 조회·변환에는 전체 절차를 적용하지 않는다. 특정 라이브러리를 미리 정하지 않고 REQ·GAP·실행 환경·평가 근거로 판단한다. 결과는 기존 INTERVIEW·AGREEMENT·DECISIONS·VERIFICATION에 기록한다.

## 1. SETUP — 입력 계약과 실행 환경

- CSV 인코딩·구분자·따옴표·헤더·결측 표기·타입·단위·날짜·ID를 파서로 확인한다. 선행 0이 있는 ID의 숫자 변환, 날짜 오해석, 잘못된 행의 묵시적 삭제를 피한다. 파일·스키마·행 수·표본 범위·해시 등 재현에 필요한 식별 정보를 기록하고 원본은 보존한다.
- 한 행의 의미, 엔터티 키·조인 관계, 중복·결측·이상값, 시간·그룹 구조를 확인한다. 라벨이나 비용·용량·거리·기준값이 실제로 있는지 대조한다. 필요한 정보가 없으면 GAP으로 질문하며 임의의 라벨·목적함수 가중치·제약값을 만들지 않는다.
- 런타임·설치된 패키지와 버전·사용 가능한 CPU/GPU·메모리·설치 및 네트워크 제약을 확인한다. 패키지 이름만 보고 해당 버전의 API나 solver 실행 가능 여부를 단정하지 않는다.
- ML에서는 원본·스키마 점검과 모델 선택용 탐색을 구분한다. 평가용 데이터가 이미 지정되어 있으면 경계를 지키고, 그렇지 않으면 분할 원칙을 정한 뒤 특징·타깃 관계를 탐색한다. 평가 데이터로 특징을 고르지 않는다.

## 2. DISCOVER·AGREE — 문제를 먼저 정의

| 유형 | 합의할 내용 | 담당자에게 확인할 정보 공백 |
|---|---|---|
| 최적화 | 결정변수·범위·단위, 최소/최대 목적함수, 반드시 지킬 제약과 위반 비용을 둘 수 있는 선호, 허용 오차·실행 시간 | 제약 충돌 시 우선순위, 실행 가능한 해가 없을 때 처리, 동률 규칙, 최적성 증명 필요 여부·근사해 허용 여부 |
| 지도학습 | 예측 대상·시점·기간, 당시 사용 가능한 특징, 라벨 생성 과정, 평가 지표·오류 비용, 학습/검증/테스트 분할 | 라벨 부재·지연·편향, 미래 정보, 동일 개체의 반복 행, 새 사용자·미래 기간 등 실제 적용 대상 |
| 비지도학습 | 군집·이상 탐지 등 사용 목적, 출력의 업무적 의미, 평가·사람 검토 기준 | 정답 라벨 없이 유용성을 어떻게 확인할지, 오탐·누락 처리와 검토 주체 |
| 예측 후 최적화 | 예측값이 목적함수·제약에 들어가는 위치, 예측 오차가 의사결정에 미치는 영향 | 불확실한 예측으로도 지켜야 할 제약, 예측 실패·분포 변화 시 대체 경로 |

CSV가 있다는 이유로 ML을 선택하지 않는다. 정해진 업무 규칙의 계산, 제약 아래 의사결정, 미지 값의 예측을 구분한다. 지도학습에 필요한 라벨이 없으면 확보·평가 계획을 먼저 정하고, 임의 라벨로 성능을 주장하지 않는다. 예측 정확도가 높다고 최적화 목적이나 제약 충족까지 보장되지는 않는다.

## 3. AGREE — 세 가지 구현 방식을 비교

**기본 후보는 요구사항을 충족하는 검증된 라이브러리 + 필요한 업무 로직**이다. 맞춤 설계는 문제 정의·데이터 처리·평가·결과 검증에도 필요하며, solver나 학습 알고리즘 자체를 새로 쓰는 것과 구분한다.

| 방식 | 적합한 조건 | 확인할 부담 |
|---|---|---|
| 기존 라이브러리 활용 | 목적·제약·모델·입출력이 지원되고 환경에서 실행 가능 | 실제 버전의 동작·기본값·실패 상태, 변환·통합 비용 |
| 라이브러리 + 맞춤 확장 | 핵심 계산은 지원하고 전처리·제약 모델링·목적함수·후처리 등만 특수함 | 확장 지점 지원 여부, 원래 보장이 유지되는지, 업무 제약 재검증 |
| 직접 구현 | 기존 기능·확장으로 REQ를 충족할 수 없거나, 문제가 작고 단순해 직접 구현의 정확성·유지보수를 검증할 수 있거나, 환경·실측 성능 근거가 있음 | 구현·검증 시간, 수치 안정성·최악의 복잡도, 유지보수, 증명 또는 독립 기준값 |

- 후보를 무한히 탐색하지 않는다. 먼저 가능한 대표 라이브러리 1~2개와 단순 기준 방법을 고르고 위 세 방식의 적합성을 판별한다. 사용자에게는 유력한 두 대안과 추천을 제시하고, 제외한 방식의 이유도 남긴다.
- REQ별 지원 여부를 **지원 / 확장 필요 / 미지원 / 미확인**으로 적는다. 유명세·문서 예제의 점수·import 성공만으로 적합 판정을 내리지 않는다. 필수 제약 미지원은 성능 점수로 상쇄하지 않는다.
- 해당 버전의 공식 문서·로컬 API·작은 실행으로 확인한다. 라이선스·추가 solver·바이너리 의존성·설치 시간·배포 환경·자원 예산도 비교한다. 외부 문서에 접근할 수 없으면 로컬 근거와 미확인 부분을 기록한다.
- 짧은 실험이 필요하면 질문 하나, 시간·메모리 상한, 종료 조건을 정해 대표 입력·반례로 확인한다. 본 구현을 세 방식 모두 만들지 않는다. 설치·실험 실패 시 조용히 전면 직접 구현으로 바꾸지 말고 비용·대안·한계를 알려 핵심 결정을 갱신한다.
- DECISIONS에 비교 근거·선택 이유·버린 대안·다시 선택할 조건을 기록한다. 직접 구현을 택하면 구체적 REQ의 지원 공백 또는 단순성·환경·실측 성능상의 이점, 직접 구현 부분의 범위와 검증 방법을 명시한다.

## 4. BUILD — 단순 기준 방법부터 같은 조건으로 비교

- 최적화는 작은 입력에서 전수 탐색·손계산 등 독립 기준값을 만들고, 적절하면 단순한 실행 가능 해 생성 방법과 비교한다. 실행 가능한 해를 만들 수 없다면 실패를 그대로 기록한다.
- ML은 다수 클래스·평균값·최근값 등 문제에 맞는 단순 기준 모델을 먼저 둔다. 후보 비교는 같은 데이터 버전·분할·지표·자원 예산으로 한다. 모델·임계값·하이퍼파라미터 선택은 검증 데이터로 하고 최종 테스트는 선택에 재사용하지 않는다.
- CSV 읽기·검증 → 전처리 → solver/모델 → 결과 검증 → 출력의 경계를 작게 나눈다. 라이브러리 교체가 전체 업무 로직 재작성으로 이어지지 않게 하되 범용 프레임워크는 만들지 않는다.
- 패키지 버전·실행 명령·파라미터·seed·데이터/분할 식별자·환경·시간·메모리를 기록한다. seed만으로 모든 환경의 재현성이 보장된다고 말하지 않는다. 학습과 추론에 같은 전처리를 적용하고 출력 ID·행 대응·형식을 확인한다.
- 실험 횟수·학습/탐색 시간·조기 종료·목표 수준을 미리 정한다. 기준 방법이 REQ를 충족하면 복잡한 대안을 추가할 이유를 확인한다. 실패하면 데이터·정식화·평가 방식부터 점검하고 무조건 모델이나 effort를 키우지 않는다.

## 5. VERIFY — 유형별로 다른 증거

### 최적화

- 반환 해의 변수 범위·정수성·모든 필수 제약을 허용 오차와 함께 독립적으로 검사하고 목적값을 다시 계산한다. solver 성공과 업무 요구사항 충족은 각각 확인한다.
- **최적해 / 실행 가능한 근사해 / 시간 제한·해 미발견 / 불가능 판정 / 비유계 / 오류**를 구분한다. 시간 초과를 불가능 판정으로 바꾸지 않고, 해가 반환됐다고 최적이라고 말하지 않는다. solver가 제공하면 bound·optimality gap·종료 조건을 기록하고, 제공하지 않으면 미확인으로 남긴다. [SciPy milp 공식 문서](https://docs.scipy.org/doc/scipy/reference/generated/scipy.optimize.milp.html)는 종료 상태와 bound·gap을 별도로 설명한다.
- 작은 정답 사례, 제약 충돌, 경계값·동률, 규모 증가를 검증한다. 후처리·반올림이 제약을 깨뜨리지 않는지 확인한다. 근사·휴리스틱이면 보장하지 않는 점과 실패 시 대체 경로를 명시한다.

### 머신러닝

- 실제 사용 방식에 맞춰 시간·그룹·중복 관계를 반영한 분할을 택한다. 미래에만 아는 특징·라벨 유래 변수·학습과 평가에 겹치는 개체로 인한 누수를 확인한다.
- 결측 대치·스케일링·특징 선택 등 학습이 필요한 변환은 각 학습 분할에서만 fit한다. 검증·테스트에는 transform만 적용한다. 파이프라인을 사용해도 잘못된 분할·미래 특징까지 자동으로 해결되지는 않는다. [scikit-learn 공식 가이드](https://scikit-learn.org/stable/common_pitfalls.html)의 전처리 일관성과 누수 방지 원칙을 따른다.
- 기준 모델 대비 지표, 표본 수·불균형·주요 하위집단의 오류, 비용상 중요한 오탐·누락, 실행 시간을 확인한다. 데이터와 예산에 맞는 교차검증·반복 또는 불확실성 설명을 선택한다. 한 번의 점수로 우월성을 일반화하지 않는다.
- 새 범주·결측·분포 변화·모델 로딩 및 재실행을 확인한다. 라벨 없는 방식은 지도학습 정확도를 주장하지 말고 합의한 내부 지표·안정성·업무 검토 증거와 한계를 남긴다.

## 6. 과정별 권장 effort — 모두 6.1 Sol

아래는 이 워크플로의 권장 배분이며 실제 성능 보장이나 자동 전환은 아니다. Codex의 추론 effort와 solver/학습의 계산 예산은 별도로 관리한다.

| 과정 | 권장 effort | 이유·전환 기준 |
|---|---|---|
| SETUP — CSV 파싱·스키마·환경 조사 | medium | 정해진 검사 실행·사실 정리, 의미가 모호하면 해당 분석만 high |
| DISCOVER — 목적·제약·라벨·예측 시점·평가 규칙 확인 | high | 잘못 정의하면 모든 결과가 달라지는 판단 |
| AGREE — 문제 정식화·라이브러리/확장/직접 구현 비교 | high | REQ 지원 범위와 구현·검증 비용을 함께 비교 |
| AGREE/BUILD — 복잡한 미해결 수학적 설계 | 조건부 xhigh | 비선형·조합 제약의 표현/완화, 맞춤 알고리즘의 정확성·복잡도, 복합 시간·그룹 누수 등 high 검토 후 남은 핵심 쟁점만 |
| BUILD — 파이프라인·알고리즘 구현·테스트 설계 | high | 데이터·모델·업무 규칙의 경계를 구현 |
| BUILD — 확정 실험 실행·로그 수집 | medium | 학습을 오래 돌린다는 이유로 xhigh를 사용하지 않음 |
| VERIFY — 비교 해석·최적성/제약·누수·일반화 리뷰 | high | 점수가 의미하는 보장과 한계를 판단 |
| WRAP — 선택 이유·알고리즘 심화 문답과 모범답안 | high | 실제 근거와 반례를 연결, 기록 정리는 medium |

미해결 쟁점이 해소되면 high로 돌아온다. 'ML'·'직접 구현'이라는 이름만으로 xhigh를 쓰지 않는다. 작업 체크포인트와 실험 상한은 유지하고, 추가 탐색 때문에 검증·인수인계를 생략하지 않는다.
